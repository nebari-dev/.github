# Contracts

Interfaces this repository promises to other repositories, and the files that
use them. A PR that changes a contract updates its entry here in the same PR.

### `pack-build-image.yaml` `workflow_call` interface
**Owner:** nebari-dev/.github · **Consumers:** llm-serving-pack `build-images.yaml` (6 calls), apps-pack `images.yaml`, software-pack-template `build-images.yaml`, pack-testbed `build-images.yaml` (verified: `gh search code "pack-build-image.yaml@" --owner nebari-dev --json repository,path --jq ".[].repository.nameWithOwner" && grep -n "pack-build-image.yaml@" ../pack-testbed/.github/workflows/build-images.yaml`)
**Inputs:** `image` (string, required: image name suffix), `context` (string, required: build context), `dockerfile` (string, default `<context>/Dockerfile`), `target` (string, default none), `platforms` (string, default `linux/amd64`), `push` (boolean, default `true`; `false` for pull request builds), `scan` (boolean, default `false`).
**Secrets:** `QUAY_USERNAME` and `QUAY_TOKEN`, both optional, used only when `push` is true.
**Requires of callers:** the calling job grants `contents: read`, `packages: write`, `id-token: write` and `attestations: write`. A caller without them fails at startup. With `scan: true`, nothing more; an optional `.trivyignore.yaml` at the repo root is linted and used.
**Promises:**
- Builds `context` for `platforms`. With `push: true` it pushes to `ghcr.io/<owner>/<repo>/<image>` and `quay.io/nebari/<repo>-<image>` with tags `sha-<short sha>` and, on the default branch, `latest`, then signs and attests both by digest.
- With `scan: false` the job behaves as it did at `ad70045`.
- With `scan: true` the job also exports a `linux/amd64` build of the same context, Dockerfile and target as an OCI layout directory in `$RUNNER_TEMP` (`provenance: false`, `sbom: false`, so no attestation manifest) and scans it with the `trivy-scan` action for fixable CRITICAL and HIGH vulnerabilities. Only `linux/amd64` is scanned, whatever `platforms` is. No SARIF is written at build time. The job summary lists each finding's CVE, package, installed version, fixed version and severity.
- `push: false`: a finding, an ignore-file lint problem or a Trivy run that fails to execute fails the job (absolute gate: every fixable CRITICAL or HIGH finding blocks).
- `push: true`: the scan never changes the job result. Findings, lint problems and Trivy execution failures become the job summary plus a warning annotation.
- Step order is part of the promise: build; export (if `scan`); `_dot-github` checkout (if `push` or `scan`); sign GHCR and sign Quay (if `push`); scan (if `scan`). The export runs before the checkout, so the checkout never lands inside a build context, and signing runs before the scan, so a scan-tool failure cannot leave a pushed image unsigned. On a push build an export failure does not stop the job: signing still runs, and the scan reports the missing export as an error through the job summary and a warning annotation. On a `push: false` build an export failure fails the job.
**Since:** 2026-11-26 (spec: nebari-dev/llm-serving-pack docs/superpowers/specs/2026-11-26-pack-cve-scanning-and-renovate-design.md (not committed))

### `pack-scan-images.yaml` `workflow_call` interface and its SARIF category names
**Owner:** nebari-dev/.github · **Consumers:** none yet; planned: pack-testbed `scan-images.yaml`, llm-serving-pack `scan-images.yaml` (schedule and manual) and `build-images.yaml` (pull requests touching `charts/**` or `.trivyignore.yaml`) (verified: `gh search code "pack-scan-images.yaml@" --owner nebari-dev --json repository,path --jq ".[].repository.nameWithOwner"`)
**Inputs (all strings):** `chart-path` (required: directory containing `Chart.yaml`); `values-files` (required: newline-separated, relative to the repo root, used by both legs); `source-values-files` (default empty: extra files for the source leg only, such as tag overrides for `main`); `chart-name` (default empty: release tag prefix; empty turns the released leg off; the released leg is not implemented yet); `image-env-regex` (default `_IMAGE$`); `extra-images` (default empty: newline-separated references scanned in addition to the rendered ones); `first-party-prefixes` (default empty: newline-separated repository prefixes treated as ours); `ignorefile` (default `.trivyignore.yaml`: applied to our images only). Blank lines and surrounding whitespace in the newline-separated inputs are ignored.
**Requires of callers:** the calling job grants `contents: read` and `security-events: write`; a base values file that turns on every image-bearing component and sets no image tag. Scanned images must be pullable without credentials.
**Promises:**
- Jobs: `trivy-db` downloads the Trivy vulnerability database and the Java database once per run into the actions cache, keyed by Trivy version, UTC date and 6-hour slot, and passes that key to every scan job, which restores that copy (also when the run crosses a slot boundary). `collect` renders the chart at the checked-out ref (`helm dependency update` first, as `pack-release.yaml` does, so a chart with dependencies renders with or without a `Chart.lock`; then `helm template <chart-path>` with one `-f` per `values-files` line, then per `source-values-files` line; Helm v3.18.2) and turns the render into a matrix with `collect_chart_images.py --leg source`, listing every image with its origin in the job summary. `scan` runs one job per image with `fail-fast: false`.
- Ours: an image whose repository is under `ghcr.io/<owner>/<repo>/` of the calling repo (lowercased) or under a `first-party-prefixes` entry. Everything else is third-party.
- Every scan job scans its image for fixable CRITICAL and HIGH vulnerabilities with the `trivy-scan` action, writes the findings table to the job summary, and uploads SARIF to code scanning under category `trivy/<leg>/<slug>`. This version has only the `source` leg, so the category is `trivy/source/<slug>`. `<slug>` is the image repository without tag or digest, with every run of non-alphanumeric characters replaced by `-` (for example `ghcr-io-nebari-dev-llm-serving-pack-operator`, `redis`), so alerts carry over a version bump. SARIF is uploaded even when the job fails on findings.
- An image of ours is scanned with `ignorefile` and fails its job on any finding not covered by a valid ignore entry, on an ignore-file lint problem, and when the scan cannot run. Exception, on `pull_request` only: the calling repo's own image referenced by tag `latest` or no tag, with no digest, is scanned and its findings are reported without failing the job (a scan error still fails it). Images matched by `first-party-prefixes`, and the calling repo's own images at any other tag (such as `sha-<short>`), fail on every trigger.
- A third-party image is scanned with no ignore file and its findings are reported in the summary and the Security tab. With findings, its job fails only when something newer exists: a newer release on the pinned tag's line, or, when the reference pins a digest, a different digest served today for the pinned tag (a re-pushed tag counts). The job lists the repository's tags with `skopeo list-tags` and reads the tag's digest as the sha256 of `skopeo inspect --raw` (up to 3 attempts each), decides with `check_image_freshness.py`, and on failure puts its one-line message in an `::error::` annotation and the summary. Otherwise the summary says "no newer release on this line; reported only" and the job passes. A third-party image without findings is not checked.
**Errors:** a scan that errors (image not pullable, Trivy could not run, ignore-file lint problem) fails its job for every origin and on every trigger; no SARIF is uploaded for it. A freshness check that cannot run (registry still unreachable after 3 attempts, a reference with no version tag) fails the job with "Cannot evaluate freshness rule". The `collect` job fails, and no image is scanned, on a failed render, a missing values file, an empty image list, an image reference containing whitespace, a control or format character, or starting with `-`, or two images whose references share a slug. A failed `trivy-db` job skips every scan job. SARIF upload is skipped on pull requests from forks, which get a read-only token, and for a job whose scan errored (no SARIF was written).
**Since:** 2026-11-26 (spec: nebari-dev/llm-serving-pack docs/superpowers/specs/2026-11-26-pack-cve-scanning-and-renovate-design.md (not committed))

### Composite action `trivy-scan`
**Owner:** nebari-dev/.github · **Consumers:** `.github/workflows/pack-build-image.yaml`, `.github/workflows/pack-scan-images.yaml`. Not meant to be called from other repos (verified: `git grep -n "actions/trivy-scan" -- .github`)
**Inputs (all strings):** `image-ref` or `input` (exactly one: a registry reference, or an OCI layout directory from buildx `type=oci,tar=false`); `ignorefile` (default `.trivyignore.yaml`; linted with `lint_trivyignore.py` and used only if the file exists; empty means none); `fail-on-findings` (default `"true"`); `sarif-file` (default empty; when set, SARIF is also written there); `title` (job summary heading, defaults to the scan target); `findings-file` and `baseline` (reserved, not implemented: setting either gives `result=error`); `warm-only` (default `"false"`; `"true"` installs Trivy and restores or downloads the databases into the cache under the same key a scan uses, then stops without scanning or writing a summary; `image-ref`, `input`, `findings-file` and `baseline` must then be empty, and `result` is `clean` when the databases are ready, else `error`); `cache-key` (default empty: when set, used as the Trivy DB cache key instead of the clock-derived one, so the jobs of one run share a key).
**Outputs:** `result`: `clean`, `findings`, or `error` (bad inputs, ignore-file lint problems, or Trivy could not run); `cache-key`: the Trivy DB cache key used.
**Promises:** scans `linux/amd64` with Trivy v0.76.2 (release tarball sha256 checked) using `--scanners vuln --severity CRITICAL,HIGH --ignore-unfixed`. Trivy databases are cached per 6-hour UTC slot (key `trivy-db-v0.76.2-<UTC date>-<slot 0-3>`, or the `cache-key` input when set), and downloaded with up to three attempts on a miss. Writes a findings table (CVE, package, installed, fixed, severity) or the error to the job summary, and lists findings and lint problems in the log. Needs no permissions and uploads nothing.
**Exit behavior:** `clean` always exits 0. Otherwise, with `fail-on-findings: "false"` it exits 0 and emits a `::warning::`; with any other value it emits an `::error::` and exits 1.
**Since:** 2026-11-26 (spec: nebari-dev/llm-serving-pack docs/superpowers/specs/2026-11-26-pack-cve-scanning-and-renovate-design.md (not committed))

### `lint_trivyignore.py` CLI and the `.trivyignore.yaml` subset it accepts
**Owner:** nebari-dev/.github (the file format itself is Trivy's, experimental at v0.76.2) · **Consumers:** `trivy-scan`; planned: llm-serving-pack's gate job in `build-images.yaml`, which runs it directly; every adopting pack's `.trivyignore.yaml` (verified: `git grep -n "lint_trivyignore" -- .github`)
**Usage:** `python lint_trivyignore.py FILE [--today YYYY-MM-DD]`. Needs `ruamel.yaml` (pinned to `0.19.1` by its callers).
**Promises:** accepts only the top-level key `vulnerabilities`, a list of entries. Each entry needs a non-empty `id` and `statement`, an `expired_at` that is an unquoted YAML date or datetime (a quoted string is rejected because Trivy cannot parse it) no more than 45 days after today (a past date is accepted on purpose: Trivy drops expired entries, so the scan then fails on the CVE), and a scope: `purls` or `paths`, each a non-empty list of non-blank strings when present. Every purl carries a version (`@version`), and a `paths` entry made only of wildcards and slashes (`*`, `**`, `**/*`) is rejected because it would suppress the CVE everywhere.
**Errors:** exit 0 clean; exit 1 with one line per problem on stdout, formatted `<entry id or index>: <problem>`; exit 2 for a usage error or an unreadable file or YAML.
**Since:** 2026-11-26 (spec: nebari-dev/llm-serving-pack docs/superpowers/specs/2026-11-26-pack-cve-scanning-and-renovate-design.md (not committed))

### `check_image_freshness.py` CLI
**Owner:** nebari-dev/.github · **Consumers:** `.github/workflows/pack-scan-images.yaml` (scan job, third-party images with findings) (verified: `git grep -n "check_image_freshness" -- .github`)
**Usage:** `python check_image_freshness.py REF --tags-file FILE [--tag-digest sha256:...]`. REF is the image reference as rendered; FILE lists the repository's tags, one per line; `--tag-digest` is the digest the registry serves today for REF's tag (pass it only when REF pins a digest). Standard library only, Python 3.10 or later.
**Promises:** a tag counts as newer only when it parses as a version (`v?N(.N)*` with an optional `-alpha.N`/`-beta.N`/`-rc.N` and an optional `-<variant>`; `latest`, `sha-...`, signatures and the like are ignored), has the same variant as the pinned tag, is on the same line (same major for 1.x and above, same `0.y` for 0.x), and sorts above it (`v1.2.3` equals `1.2.3`, `18.4` equals `18.4.0`). Pre-releases count only for a pre-release pin of the same release and train. Because the variant must be equal, a build-stamped pin such as `18.0-<timestamp>-system-trixie` would compare only with tags carrying the same timestamp (the timestamp is part of the variant), so no tag would ever count as newer and, as such tags are not re-pushed, the digest check would not fire either. Rolling tags compare normally: the cloudnative-pg chart's `18.4-system-trixie` is compared against every `18.x-system-trixie`. A newer tag is reported before a moved digest.
**Errors:** exit 0 nothing newer, nothing on stdout; exit 1 something newer, exactly one line on stdout, either `<REF>: newer release <tag> on the line of <pinned>` or `<REF>: digest <old> -> <new>` (callers show it verbatim and do not parse it); exit 2 for a usage error, a REF without a version tag, or an unreadable tags file (message on stderr).
**Since:** 2026-11-26 (spec: nebari-dev/llm-serving-pack docs/superpowers/specs/2026-11-26-pack-cve-scanning-and-renovate-design.md (not committed))
